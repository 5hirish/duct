The window is not the container

Our UI is responsive to the browser. It is not yet adaptive to the desktop.

1 Sep 2026 Scope app/src — layout, units, shared components Status audited · first fixes shipped Branch feat/gads-connectors-wave2

The short version

Duct ships the same build to a browser and to a Tauri window. The browser side is handled: there are breakpoints, the sidebar collapses, panes toggle on phones. The desktop side is where the gap is, and it is one specific gap repeated in several places — components size themselves off the viewport when the thing that actually constrains them is a resizable pane.

The desktop shell opens at 1200×800 and can be dragged down to 900×600 (desktop/src-tauri/tauri.conf.json). That matters: 900px is below Tailwind's lg breakpoint and above its md, so the desktop window spends its whole life inside a band the layout treats as "big tablet". Nothing in the app knows it is a desktop app.

The one-sentence finding. Three agent workspaces put a chat pane and a report pane side by side behind a draggable divider — and every component inside those panes still asks the window how wide it is. At 1440px of window with the divider at halfway, a component sees "1440px, go wide" and renders a four-column board into a 700px pane.

Viewport versus container

This is the finding worth internalising, because everything else on the list is tidying by comparison.

SplitWorkspace is a good abstraction — audit, content and insights all compose it rather than re-forking the divider. But it hands each consumer a pane whose width is a user-dragged percentage of the window, clamped between 20% and 80%. A component rendered into that pane has no fixed relationship to the viewport at all. Two panes, one window width, and a divider the user moves whenever they want: viewport media queries cannot describe that.

Container queries are the right tool and they are no longer a bet: they reached Baseline widely-available status in August 2025 and sit around 92% support, and Tailwind v4 — which we are already on at 4.2 — ships @container and the @md:-style variants with no plugin. The current guidance is a clean division of labour: media queries for page structure, container queries for components, clamp() for fluid type and spacing. We use exactly one of those three.

Caveat worth knowing before the refactor

Containment is not free. An element cannot query itself — only its children can query it — so the pattern usually needs a wrapper. Flex and grid children need explicit or intrinsic sizing or content collapses, and custom properties are not allowed inside @container conditions. Expect a wrapper div per adapted component rather than a one-line class swap.

On "relative"

globals.css carries 485 absolute pixel values against 19 rem, and the JSX adds 230 more as Tailwind arbitrary values like h-[80px] and min-w-[280px]. It is worth being precise about what that does and does not cost, because the usual scare story does not apply cleanly to a desktop webview.

What it does not break: OS display scaling. When Windows runs at 150% or a Mac drives a Retina panel, the webview scales the CSS pixel itself, so a 52px header comes out physically larger without our help.

What it does break: the user's text-size preference. A reader who raises their default font size, or uses text-only zoom, moves rem and em and nothing else. Every font-size: 13px in our stylesheet — and there are dozens — silently refuses that request. On a desktop app people keep open all day, that is the accessibility cost that actually lands.

The second cost is coherence. Nine hand-picked CSS breakpoints (480, 520, 540, 740, 780, 860, 900, 960) sit alongside Tailwind's four, so a layout can change at 860px in the stylesheet and again at 768px in a class on the same element, and neither author can see the other's decision. Alignment matters more than the specific numbers.

Recommended target, in priority order: type and spacing in rem; fluid steps via clamp() for the handful of things that should scale with the window; one breakpoint scale (Tailwind's) for page structure; @container for anything rendered inside a pane. Borders, hairlines and icon sizes can stay in px — they are genuinely device units.

What the platform asks for that we are not doing

Input: pointer events, not mouse events

The divider listened for mousedown and then tracked mousemove on window. Every consumer of SplitWorkspace renders an <iframe> in the right pane — the audit report (AuditReport.jsx:318), the insights report (InsightsWorkspace.jsx:442), the slide preview (SlidesCarousel.jsx:99). An iframe is a separate event target, so the moment the cursor crossed into one, the move events stopped arriving and the drag died mid-gesture. The Pointer Events API fixes both halves of this: one code path for mouse, trackpad, pen and touch, and setPointerCapture to keep the events coming back to the handle no matter what is underneath.

Keyboard: a splitter you can actually move

The W3C window splitter pattern is specific. The handle takes role="separator", is focusable, and carries aria-valuenow / aria-valuemin / aria-valuemax, an accessible name, and aria-controls pointing at the primary pane. Arrow keys move it, Shift + arrow moves it further, Home and End go to the extremes, and Enter collapses and restores. We had none of it. On the platform where the keyboard is the primary input, a control only a mouse can reach is not really a control.

Density and reach on a big screen

The large-screen guidance is consistent across Android/ChromeOS and the older Windows UX material: a desktop can carry higher visual density than a phone because the pointer is precise, but reading measure should still be capped — 50–75 characters is the target, 100 the ceiling. Our .app-main caps at 1440px, which is a reasonable structural cap, but the text inside it is not measure-capped, so prose in a full-width report gets long on a wide monitor. Worth a max-width in ch on the prose blocks specifically.

Three webviews, not one browser

The shell renders in WKWebView on macOS, WebView2 on Windows and WebKitGTK on Linux, and they disagree at the edges of newer CSS. We use oklch() throughout the token layer, color-mix() in several places and backdrop-filter on the header. All are well supported now, but none of it is verified on WebKitGTK, which is the laggard of the three and the one none of us runs. That is a testing gap, not a code defect — but it is the gap most likely to produce a bug report we cannot reproduce.

Modularity: what is shared, what was forked

The architecture here is better than the details. SplitWorkspace and PipelineProgress are both real shared abstractions with three consumers each and no forks — the earlier decision to extract them held. The problem is one layer down, in the small pieces nobody thought were worth a shared home.

Was duplicated

The agent primitives

audit/CodeBlock.jsx and content/CodeBlock.jsx differed only in comments. auditPhase.js and contentPhase.js were byte-identical — a six-member enum describing the agent lifecycle, forked so that adding a phase meant editing two files or letting them drift.

Was duplicated

The busy ring

Twelve hand-written spinners across eighteen files, in four border colours (current, primary, blue-500, orange-500) and six sizes. Two of the twelve told a screen reader anything at all. "The app is working" looked like a different thing on every surface.

Still to do

The global stylesheet

2,077 lines, 247 class selectors, and the prefixes give it away: rpt- (33), conn- (28), generate- (27), kpi- (23), signin- (21). This is per-page styling in a global file — the opposite of the component model the rest of the app follows.

Still to do

The long files

AuditReportV1.jsx (957), execute/page.jsx (921), onboarding/page.jsx (851), connections/page.jsx (800). Not wrong on their own, but each is a place where a shared piece gets written inline instead of extracted, because extracting is a bigger edit than inlining.

A component that owned a height it could not know

PlanBoard was h-[calc(100vh-15rem)] — a number tuned for one of its two callers. It renders both in the scrolling /content tab and in the full-bleed /content/plan route, where the parent already has a definite height and the viewport maths is simply wrong. A component that hardcodes its own height cannot be reused in a second layout; the caller has to own that.

What I changed

All of it is committed on feat/gads-connectors-wave2 and the production build passes. Each item below names the file it landed in, so the claims here can be checked against the code rather than taken on trust.

01

SplitWorkspace, rewritten for the platform

app/src/components/workspace/SplitWorkspace.jsx — one file, three consumers.

  • Pointer events with setPointerCapture, so the drag survives the iframes in the right pane; touch-action: none on the handle.
  • role="separator" with the full ARIA value set, plus arrow / Shift-arrow / Home / End / Enter-to-collapse per the W3C pattern, and a visible focus state.
  • Cursor and user-select pinned to the body for the duration of a drag, so text stops selecting under the gesture.
  • Double-click resets to the default split.
  • A note at the point of temptation explaining why the panes themselves are not containers — see below.
  • The stored ratio now loads in an effect rather than during the first render — reading localStorage in a useState initialiser made the client disagree with the prerendered HTML — and the read is guarded, so a webview with storage disabled falls back instead of throwing.
02

The first container-adaptive component

PlanKanban moved from sm:grid-cols-2 lg:grid-cols-4 to @md:grid-cols-2 @4xl:grid-cols-4. It now collapses to one column in a narrow pane and opens to four when it has the room, at any window size — correct in both of its call sites for the first time.

03

The insights session fills the window

/insights/session joined FULL_BLEED_PREFIXES, and its h-[calc(100vh-4rem)] became h-full. It had been subtracting 64px for a 52px header while sitting inside .app-main's 28px top and 64px bottom padding — so the one agent surface that should fill the window was instead taller than it, and scrolled.

04

Height belongs to the caller

PlanBoard is now h-full. The full-bleed route gives it a height directly; the scrolling tab — the one caller that genuinely has no height above it — states its own, in svh to match the rest of the app.

05

Shared primitives, three fewer forks

  • workspace/CodeBlock.jsx — one copy; the duplicate is deleted and both chats import it.
  • workspace/agentPhase.js — the lifecycle enum, shared, with a comment saying why it lives there.
  • ui/spinner.jsx — one busy ring. Colour comes from currentColor so callers tint it like text; size and overrides go through className and tailwind-merge replaces rather than fights the defaults. Decorative by default, with an opt-in label that turns it into a live role="status" for the cases where the ring is the only signal. Adopted at all twelve sites.
A trap worth recording

My first pass put container-type: inline-size on both panes, so any descendant could query the pane directly. That is wrong here, for exactly the containment side effect the research flags: container-type implies contain: layout, which makes the element a containing block for position: fixed descendants. Three full-screen overlays render inline inside these panes rather than through a portal — audit's ExecutionOffer, content's PublishModal and ContentChat's image lightbox, all fixed inset-0. A container on the pane would have quietly shrunk all three from full-screen to pane-sized.

So containers are declared per component instead, at the component's own root — which measures effectively the same width. Portal those three overlays to <body> and the pane-level container becomes safe; that is on the backlog below, and worth doing on its own merits.
