每个产品团队都运行 8–12 个工具。每个工具都只看到一小部分。我厌倦了充当它们之间的集成层，所以我写了一个。然后我把它放在 GitHub 上，采用 MIT 许可，因为一个读取你整个业务的东西必须是可读的。

01

没人谈论的问题

你的分析工具知道发生了什么。你的支持工具知道谁不满意。你的项目追踪器知道发布了什么。你的广告平台知道你花了多少钱。但它们之间互不相通——所以每周都有人手动在它们之间传递数据，决策则根据当时打开的某个片段做出。故事一直都在那里。只是没有人完整地阅读它。

02

于是我将它们连接起来

Duct 读取你已运行的工具，并回答它们都无法单独回答的问题：为什么会发生这种变化，我们该如何应对。它不是另一个仪表盘，也不是另一个你会在第三季度放弃的数据仓库项目。当答案是“暂停该广告系列”或“标记该 GA4 事件”时，Duct 可以准备变更并向你显示预览。它无法应用变更。只有你可以。这个界限存在于代码中，而不是在提示中。

03

然后我开源了它，原因如下

授予一个工具读取你的广告、分析和收入的权限是一件大事，而授予一个由一个人构建的工具更是如此。我不能要求这种信任；我可以展示代码。每个提示、每个 API 调用以及批准门本身都在 MIT 许可下的仓库中。下载应用，我为你运行服务；克隆它，则与我无关。使用你自己的密钥是免费的，并且会一直如此。付费计划稍后会捆绑模型，适用于那些不想持有任何密钥的团队。什么在哪里运行，以及什么会收费有单独的页面。

名称的由来

导管不是水源。
它是输送的。

Duct 是拉丁语——ductus，意为引导。它与 aquaeductus（输水渠）中的词根相同：水，被引导。罗马的输水渠从未制造一滴水。泉水早已存在。罗马建造的是通过重力将水从水源地输送到人们居住地的渠道。

大部分工程都是隐形的。输水渠在地下延伸数英里，不引人注目，而大家拍照的拱门只因山谷阻碍才存在。尼姆输水渠在五十公里内下降了大约十二米——站在旁边你根本看不出坡度，它在各种地形上都保持着稳定。

你的业务已经拥有数据。广告、分析、搜索、支持、收入——源头都很好。缺少的是渠道：一个能跨越十几个 API 和三个操作系统，并抵达实际做出决策的地方。当输水渠正常工作时，没有人会想到输水渠。他们只是有水可用。

Duct 的作用

目前有三个智能体。
更多正在开发中。

每个都读取十二个已连接的来源，而不是一次一个，当答案是变更时，它会准备变更并等待你。每个连接器和每个提示都在仓库中，所以这个列表就是列表，而不是路线图。

洞察

询问“为什么上周注册量下降了”，并获得一个综合了 Google Ads、GA4 和 Stripe 数据的答案。第二个智能体会在数据到达你之前重新检查每个数字，它撰写的简报会引用其来源。

SEO 审计

粘贴一个 URL。Duct 会抓取网站，读取技术和内容信号，然后返回一份优先排序的报告。这是免费的入口：无需账户即可运行。

Content Studio

看板上的一个计划，每张卡片一个帖子，为每个帖子生成幻灯片和图片，一键发布到九个网络。结果会回到卡片上，以便下一个计划从上一个中学习。

我的工作方式

原则，而非陈词滥调

行动前批准

智能体提出建议。你来决定。

Duct 默认读取。当它可以修复某些问题时，它会准备一个变更集，向你显示预览和安全检查，然后等待。智能体可以提出和检查；它不能批准或应用。该决定存在于模型永远看不到的代码中，并且回滚是合同的一部分。

实质重于形式

交付洞察，跳过噪音

我不会为了填充更新日志而构建功能。每个智能体、每个连接器和每个安全防护措施之所以存在，是因为它首先在实际决策中为我节省了真实时间。
